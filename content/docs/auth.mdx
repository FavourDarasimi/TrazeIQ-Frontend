## Dashboard sessions vs project API keys

TrazeIQ has two completely separate auth surfaces. Confusing them is the most common integration mistake.

<ParamTable params={[{"name": "Authorization: Bearer", "type": "JWT in httpOnly cookies", "description": "Reading data — every GET/PATCH/POST under /api/v1/* except /events/ ingestion."}, {"name": "X-API-Key", "type": "HMAC-hashed project key", "required": true, "description": "Writing data — only POST /api/v1/events/ (ingestion)."}]} />

<Callout variant="info" title="Envelope shape">
  Every response is `{success, message, data}` or `{success:false, message, error:{code, fields?}}`. Branch on `error.code` — never parse human `message`.
</Callout>

## OTP registration

The email is proven before a password is ever accepted. No User row exists until the final step succeeds.

<Callout variant="tip" title="Dev bypass">
  When `AUTH_DEV_OTP` is set (default `000000` in dev), that code is accepted for any pending OTP until real email delivery is wired.
</Callout>

### Step 2 — verify OTP

Returns `{data:{registration_token}}` — 64 hex chars, show once, hold in memory. Single-use, 15 min TTL; replaying it is `REGISTRATION_TOKEN_INVALID`.

## Login, refresh, logout

Short-lived access (15 min), long-lived refresh (7 days), both httpOnly. The client single-flights refresh on 401.

<Callout variant="warning" title="Brute-force lockout">
  Lockout is per `(IP, email)` pair — 5 failures lock for 15 min with `Retry-After: 900`. A successful login clears that pair's failures.
</Callout>
